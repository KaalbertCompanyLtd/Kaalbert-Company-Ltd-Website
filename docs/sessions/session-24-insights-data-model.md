## Decisions Made

- `Article.nextStepCta` modelled as one `Json` `{label, href}` column, not two scalar fields
  (contrast `Offer.ctaHref`/`ctaLabel`) — the feature doc names it as a single field this
  time, and there's no admin editor yet to need per-field editing.
- `Article.previewImage` is nullable at the schema layer even though
  `content-management-admin.md` requires the admin publish flow to demand one before
  publication — enforcement belongs at the app layer (same precedent as `EnquiryRecord`'s
  progressively-filled fields), not a `NOT NULL` constraint that would block saving an
  in-progress draft.
- `Article.categoryId` is nullable with `onDelete: SetNull`, implementing
  `content-management-admin.md`'s explicit rule that retiring a category never deletes or
  orphans its articles — they fall back to "no assigned category."
- `Category.isPlaceholder` was added beyond the feature doc's literal id/name/slug list, same
  precedent as `Capability`/`MethodStage`/`Page` — T4.4 seeds both real and illustrative
  categories and both need to be distinguishable.
- `Article.isPlaceholder` was added now, at schema-creation time, per this task's explicit
  architecture constraint — not deferred as a retrofit the way `DiagnosticQuestion`'s
  equivalent gap was.
- `ArticleResource` carries no `isPlaceholder` of its own (a child row under `Article`, same
  precedent as `OfferTier`).
- `@@index([publishedAt])` and `@@index([categoryId])` added on `Article` now, ahead of any
  query being built, specifically for T4.2's 100+-article performance requirement (FR-3.6).
- Noted for whoever picks up T4.2/T4.3: the epic file (`docs/tasks/04-insights.md`) says the
  mockups live at `ui/mockups/a-public-site/insights-index.html` /
  `insights-article.html`, but the real files are at `ui/mockups/b-insights/insights-index.html`
  and (need to confirm the article template's exact filename in that same directory at T4.3
  time) — the epic file's path is stale, not the mockup's actual location.

# Task T4.2 — Insights index — `/insights`

## What to build
Index screen to its mockup: category filter, search, article cards, performant to
100+ published articles (FR-3.6) via proper indexing on `published_at`/`category`.

## Input → Output contract
`GET /insights` and `GET /insights?category=&q=` → filtered/searched

## Acceptance criteria
Filter and search both produce shareable URLs (query params, not
client-only state); empty search results show the documented empty state, not a blank page;
draft articles never appear.

## Size / Dependencies

## Architecture constraints
- Business logic lives in `lib/`, never inline in a route handler or component: the query
  that filters by category/search and excludes drafts belongs in a `lib/` module (e.g.
  `lib/insights.ts`), called from the page/route, which only shapes the response.
- `published_at` is the single source of truth for visibility (T4.1) — every query this task
  writes must filter out rows where `publishedAt` is null; there is no `is_published` flag to
  check instead.
- `Article.categoryId` is nullable — an article with no assigned category must still appear
  on the unfiltered index, be excluded from category-filtered views, and be included in
  search/"related articles" (insights-engine.md's own documented edge case).
- Any page/route that reads live database content must export
  `export const dynamic = "force-dynamic"` — without it, Next.js may statically prerender at
  build time (Prisma calls aren't tracked by Next's fetch-cache heuristics), and on Railway
  specifically this fails the build outright (no access to `*.railway.internal` from the
  build container). Apply this to the `/insights` page now, as it's built.
- Never let a `"use client"` component (e.g. the search input, category filter control) import
  a value — not just a type — from a `lib/` file that also imports `@/lib/prisma`. If the
  index needs client-side option/lookup data (e.g. the list of categories for a filter
  dropdown), put that in its own `lib/insights-options.ts`-style file with zero import of
  `@/lib/prisma`, or pass it down as server-fetched props instead of importing it directly in
  the client component.
- Filter and search state must be real query params (`?category=&q=`), not client-only
  React state — this is both an explicit acceptance criterion and required for the
  documented "shareable URL" behaviour.
- Accessibility: WCAG 2.1 AA (NFR-2) — use Base UI primitives for the filter control (e.g. a
  Select/Combobox) and ensure the search input and category filter are both keyboard-
  operable with visible focus states, not bare unstyled `<div>`/`<input>` markup.
- Responsive is built in from first implementation, not a later pass — the mockup
  (`ui/mockups/b-insights/insights-index.html`) is a desktop-only wireframe; the filter bar,
  search input, and article card grid must all work at mobile (~375–430px), tablet (~768px),
  and desktop (~1200px+), inferring a reasonable stacked/collapsed treatment at narrower
  widths consistent with `ui/design-system.md`'s existing patterns.
- Every public page type carries `meta_title`/`meta_description`, OG/Twitter tags, and
  JSON-LD per `seo-and-search-foundation.md` — the index page itself needs its own page-level
  meta (distinct from each article's own meta, which is T4.3's concern), even though no
  single `article`/`category` row supplies it (this is a static index page's own SEO meta,
  likely hardcoded copy or a small addition to the shared `Page` model — check
  `seo-and-search-foundation.md` for how other index-style pages are expected to source this
  before inventing a new pattern).
- Do not add a CMS, headless CMS, or page-builder product (ADR 0001) — not a realistic risk
  here, but stated since this task is squarely "read the hand-built content model and render
  it."
